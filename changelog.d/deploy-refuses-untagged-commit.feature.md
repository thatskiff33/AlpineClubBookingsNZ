- **The production deploy now refuses a commit that is not a published release, and the install steps start from a release (#4978).** `scripts/run-production-blue-green-deploy.sh`, in both its deploy and its `--build-and-push-images` mode, now checks with `origin` that an annotated release tag such as `v0.13.2` points at the commit it is about to deploy. If none does, it stops before any image, workspace or migration is touched. A lightweight tag, a tag that only exists on the deploy host, and an `origin` that cannot be reached are all refused too.

  **What operators need to do.** Until the next release is cut, plain `main` is not a release, so every production deploy of `main` needs the override: set `ALLOW_UNTAGGED_DEPLOY_COMMIT=1` and a written `UNTAGGED_DEPLOY_COMMIT_REASON` in the shell (not `.env`, and pass them through if you use `sudo`). The reason is printed in the deploy log. Staging hosts that deploy `main` on purpose need the same two variables. To deploy a release instead, run `git fetch origin tag <tag>` and then `DEPLOY_REF=<tag> ./scripts/run-production-blue-green-deploy.sh`. A fork that does not tag its own releases either tags them with `pnpm run release:cut` or sets the override on every deploy.

  The install steps in the Implementation Guide and in "First Bootstrap" in `DEPLOYMENT.md` now check out the latest release tag straight after `git clone`, so a new club no longer installs whatever `main` held that day. The three `v0.10.0` draft files moved to `docs/releases/drafts/`, so `docs/releases/` lists only published releases.
