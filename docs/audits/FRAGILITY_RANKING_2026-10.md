# Fragility ranking: where bugs came back (October 2026)

Audience: Maintainer

This is the second half of Goal 1's first move ([GOALS.md](../GOALS.md#first-move-find-where-bugs-come-back)):
the 15 business areas confirmed by the owner
([recorded on #4024](https://github.com/thatskiff33/AlpineClubBookingsNZ/pull/4024#issuecomment-6113045008),
11 Oct 2026)
([FRAGILITY_AREAS_PROPOSAL.md](FRAGILITY_AREAS_PROPOSAL.md)), ranked by
**bugs that came back**. Every Phase 1 sweep starts with the areas at the top.

A repeat is a pair: an earlier fix, then a later change that fixes the same
problem again — because it broke again, because the first fix did not hold or
missed part of the problem, or because the first fix itself caused the later
bug. Total bug volume does not count: an area with many unrelated fixes and no
repeats ranks low.

## How to read this

- **Confirmed repeats** counts pairs across all history since the first commit
  (3 Apr 2026). **Since 8 Aug** counts the pairs whose later side landed on or
  after the 8 Aug audit (epics #2680, #2725). An area whose repeats are mostly
  before 8 Aug has cooled down; one whose repeats are mostly after it has not.
- Each pair counts once, in the one area its recurring problem belongs to, so
  the columns add up to the total.
- A **chain** is pairs that share a fix (A → B, B → C): one problem coming
  back more than once. Each line names the earlier fix → the later re-fix or
  re-break, the signals that found it (each linked to its evidence) and the
  one-sentence reason it was confirmed, so any line can be checked by hand.
- This ranks where to look first. It is not a root-cause analysis, and nothing
  here was fixed or filed.

## How the method works

1. **Collect.** Every issue, PR and comment on GitHub (4,031 issues and PRs,
   6,783 comments, PR bodies included), and every fix on `main`: 513 fix units,
   one per merged fix PR plus each `fix…` commit made straight on `main`.
2. **Find candidate pairs.** Four signals each propose earlier fix → later
   fix (or later issue) pairs, 621 in all (a pair more than one signal
   found counts under each, so the four counts add up to more):
   - **code-history overlap** (224): the later fix rewrote at least five lines
     that `git blame` says an earlier fix, for a different issue, had written;
   - **text citation** (397): an issue, PR body or comment cites an earlier,
     already-fixed issue or PR in the same sentence as "again", "regressed",
     "reintroduced", "came back", "still" and similar;
   - **re-fix of the same issue** (29): one issue needed a second fix unit;
   - **revert** (1): a fix commit was reverted.
3. **Screen out known noise** (316 pairs): citations whose only repeat word is
   "still", and re-fixes landing under three days after the first fix. Part 1's
   spot checks found both are nearly always incidental or one issue delivered
   over several PRs.
4. **Judge every remaining pair by hand** (305). Each pair was read from both
   fixes' diffs and commit messages, and from the citing text where there was
   one. A pair is **confirmed** when the later change fixes the same problem
   again: it broke again, the earlier fix did not hold or missed part of the
   problem (including a residual the earlier PR recorded and left open), or
   the earlier fix itself caused the later bug — including a reintroduction
   caught in review before merge. It is **rejected** when the overlap is a
   different bug in the same code, a feature, a refactor or move, a test-only
   change, or a planned next step of the same work. Unclear pairs were
   rejected. A confirmed pair goes in the one area its recurring problem
   belongs to, whatever files it touched.
5. **Rank** areas by confirmed pairs, then by pairs since 8 Aug, then by list
   order. Each verdict, with its area and reason, is in
   [FRAGILITY_RANKING_2026-10.verdicts.json](FRAGILITY_RANKING_2026-10.verdicts.json);
   the generated block above is built from it.

## How precise it is

- **Each confirmed pair has been read by hand,** so the ranking counts judged
  repeats, not raw signal hits. The judging was split across reviewing agents,
  one batch each; the orchestrating agent spot-checked a sample against the
  diffs and made every area assignment consistent, moving two pairs so one
  chain sits in one area.
- **How often each signal held up**, out of the pairs judged:

  | Signal | Judged | Confirmed |
  | --- | --: | --: |
  | code-history overlap | 224 | 123 (55%) |
  | text citation | 82 | 22 (27%) |
  | re-fix of the same issue | 4 | 1 |
  | revert | 1 | 1 |
  | more than one signal on the same pair | 6 | 5 |

  A pair with more than one signal counts under each of its signals and in
  the last row, so the rows add up to more than the 305 judged and 142
  confirmed. These match part 1's spot checks (about 6 in 10 and 2–3 in 10). A pair two
  signals agree on is nearly always real.
- **Recall is lower than precision.** A repeat is missed when the later fix
  rewrote new lines rather than the earlier fix's, nobody cited the earlier
  fix, and the issue was never reopened. The `reopened` signal is empty this
  run: reading reopen events anonymously would take about 300 more pages at
  60 an hour. Fixes that were never labelled as fixes (a `feat` that repaired
  something) are not fix units, so their repeats are missed too.
- **Judgement calls lean one way.** "When unclear, reject" keeps borderline
  pairs out, so counts are a floor. The borderline cases most often concerned
  later features that invalidated an earlier fix's assumption (rejected) and
  residuals an earlier PR recorded and a later PR closed (confirmed).
- **Areas are counted, not weighted.** One wide incident can confirm several
  pairs against one later PR (for example PR #3712 and PR #3713 in Xero), so
  read the chains column with the count: a high count with few chains is one
  or two problems that kept coming back.

## Reproducing it

Measured at `main` `3ca2f399deaded6f263300b7e299f0e0310a2503` (12 Oct 2026
NZ), over the full history, with GitHub issues, PRs and comments as they stood
at 2026-10-11T16:33:33Z (the moment the run read them: 4,031 issues and PRs,
6,783 comments). This regenerates the generated block above exactly:

```
pnpm run audit:fragility:collect -- --anonymous --ref 3ca2f399deaded6f263300b7e299f0e0310a2503
pnpm run audit:fragility:signals -- --github-until 2026-10-11T16:33:33Z
pnpm run audit:fragility:rank -- candidates       # tmp/fragility/candidates.json, for judging
pnpm run audit:fragility:rank                     # rewrites the generated block from the verdicts
```

- **Re-checked on 27 Oct 2026** with the scripts as merged with `main` at
  `56fceba35f27`: every ranked count, all 305 judged pairs and the 142/163
  split came out identical. The original 12 Oct run counted one more
  text-citation pair (622 candidates, 398 citations, 317 screened out); that
  pair was screened out as noise, never judged, and its text has since been
  edited or deleted on GitHub, so the figures here are the ones a rerun
  produces.
- **Use `--anonymous`, not a token, to reproduce.** A token also collects
  reopen events, which adds two `reopened` pairs this run never judged
  (`pr-1480->issue-1479`, `pr-1919->pr-1921`), and the last step then refuses
  to run until they have verdicts. The anonymous collection takes about two
  hours.
- The last step refuses to run while any screened candidate has no verdict, so
  a rerun on a newer `main` (or without `--github-until`) first needs verdicts
  for its new pairs. Output lands in `tmp/fragility/` (git-ignored).
